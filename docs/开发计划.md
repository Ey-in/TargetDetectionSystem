## 四、GPU 与训练安排

> 训练会长时间占满 GPU，多人同时跑会互相拖慢甚至 OOM。**不排期就会出现"谁都跑不动"**。

| 项 | 说明 |
|---|---|
| GPU 资源 | 待填（谁有、什么型号、显存多大） |
| 训练负责人 | 待定（建议 1 人主责，其他人不抢卡） |
| 排期方式 | 在本节列出预约时段：`日期 | 使用者 | 任务 | 预计时长` |
| 无卡组员怎么办 | 用**冻结的预训练模型**开发界面与流程（即 walking skeleton 的思路），不受训练进度阻塞 |

**约定**：训练脚本必须放在 `src/` 之外或明确标注为实验代码，训练日志与超参记录归档到
`exp/` 分支并在 PR 中留痕 —— 课程要的"工作量证明"包括这些过程。

## 五、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 演示现场无 GPU，CPU 推理过慢 | 演示失败 | M2 起就在 CPU 上验证；M4 专门做无 GPU 回归（T-32） |
| 模型训练效果不佳（mAP 低） | 演示观感差 | 采用预训练权重微调而非从零训练；准备一组"一定能检出"的演示样例 |
| 视频处理耗时过长 | 演示卡住 | 提前录制短样例视频；M2 起就测真实耗时 |
| 组员环境不一致 | "在我这能跑" | 锁定 `requirements.lock.txt`；`setup-dev.ps1` 一键搭建 |
| 后期需求膨胀 | 做不完 | 需求文档 1.2 节明确"不做什么"；新需求走变更记录 |
| 文档最后突击补写 | 与实现脱节，答辩被问穿 | 文档随 PR 同步更新（见 CONTRIBUTING 第七节） |
