# 仓库设置清单（配置管理员）

本清单是在 GitHub **网页上**做的一次性设置，只有仓库管理员能操作。
命令行无法代劳（本机未装 `gh`，且当前网络下 GitHub API 的 https 走不通）。

> **开始前：确认代理 / VPN 正在运行**，否则网页打不开或加载不全。

## 执行顺序很重要

```
① 首个 PR 合并  →  ② CI 跑过一次  →  ③ 才能设置分支保护
```

**必须先合并首个 PR 再设分支保护。** 原因：分支保护里"要求状态检查通过"的下拉列表，
只在 CI 至少运行过一次之后才会出现 `lint-and-test` 这一项。顺序反了会发现搜不到，以为配错了。

## ☐ 1. 添加 LICENSE 文件

项目以 AGPL-3.0 发布（理由见 README「许可证」一节）。

1. 仓库首页 → **Add file** → **Create new file**
2. 文件名填 `LICENSE`
3. 右侧出现 **Choose a license template** → 选 **GNU Affero General Public License v3.0**
4. Commit

> 用官方模板而不是手抄，是为了拿到准确的法律文本。

## ☐ 2. 设置 main 分支保护

GitHub 现在有两套界面，任选其一。

**新版（Rulesets）** — Settings → **Rules** → **Rulesets** → New ruleset → New branch ruleset

- Ruleset Name：`protect-main`
- Enforcement status：**Active**
- Target branches：Add target → **Include default branch**
- 勾选：
  - ☑ **Require a pull request before merging** → Required approvals 填 `1`
    → 展开后勾 ☑ Dismiss stale pull request approvals when new commits are pushed
  - ☑ **Require status checks to pass** → 搜索并选中 `lint-and-test`
  - ☑ **Block force pushes**
- Bypass list：**留空**（含管理员，这样规则才真的强制）

**旧版（Branch protection rules）** — Settings → **Branches** → Add branch protection rule

- Branch name pattern：`main`
- ☑ Require a pull request before merging → Require approvals：`1`
- ☑ Require status checks to pass before merging → 搜索 `lint-and-test`
- ☑ Do not allow bypassing the above settings

**验收方式**：本地在 main 上随便改点东西尝试 `git push origin main`，**必须被拒绝**才算配好。

## ☐ 3. 邀请组员

Settings → **Collaborators** → Add people → 输入每人 GitHub 用户名。

> 仓库是公开的，组员其实**不邀请也能 clone**（公开仓库人人可读），
> 但**要能推送分支、开 PR，就必须被邀请为协作者**。所以这一条不能省。

收到用户名后，同步回填：
- `docs/团队与角色分工.md`（成员 ↔ 角色）
- `docs/开发计划.md`（任务表里的负责人）
- `CODEOWNERS`（目前**刻意未创建** —— 占位符状态下它非但无效，还可能静默挡住合并。
  用户名到齐后再补上，格式见文件末尾附录）

## ☐ 6. 建看板 Projects

Projects → New project → **Board** 视图，列建议：

```

```

把 Milestone 设为 M1 的 Issue 拖进去即可。看板不是给老师看的，是为了每次周会能一眼看到
"谁卡住了"。

## ☐ 7. 核对提交邮箱（**不做这一步，工作量证明会失真**）

GitHub → Settings → **Emails**，确认本地 `git config user.email` 用的那个邮箱
（当前是 `3271484571@qq.com`）已**添加并验证**。

**没验证的后果**：提交不会关联到你的账号，头像显示不出来，`scripts/worklog.ps1` 统计出的
贡献数据助教无法核实 —— 而"版本控制日志"正是课程点名要的工作量证明。

若该邮箱无法验证，改用 GitHub 提供的 noreply 地址（在 Emails 页面能看到形如
`<ID>+<用户名>@users.noreply.github.com`），并在本仓库内覆盖：

```powershell
git config user.email "<你的 noreply 地址>"
```

**每位组员都要各自核对一遍。**

## ☐ 8. 合并首个 PR 后打基线标签

首个 PR（脚手架）合并进 main 之后：

```powershell
git checkout main
git pull
git tag -a v0.1-需求基线 -m "仓库脚手架与协作规范就绪"
git push origin v0.1-需求基线
```

之后每个里程碑合入 main 时都打一个 tag（`v0.2-概要设计基线` …）。
GitHub 会据此自动生成 release notes —— 这正是我们**不用**手工维护 CHANGELOG 的原因。
tag 同时是"配置项基线"，是配置管理员的职责产出。

## 附录：CODEOWNERS 补写格式

组员用户名收齐后，创建 `.github/CODEOWNERS`（**不要现在就建**，占位符会静默挡住合并）：

```
# 默认所有改动需要技术经理评审
*                       @<技术经理用户名>

# 检测与后处理核心
/src/detect/            @<模型负责人用户名>
/src/postprocess/       @<模型负责人用户名>

# 文档
/docs/                  @<项目经理用户名>
/提交物/                 @<项目经理用户名>

# CI 与仓库配置
/.github/               @<配置管理员用户名>
/scripts/               @<配置管理员用户名>

# 测试
/tests/                 @<测试工程师用户名>
```
